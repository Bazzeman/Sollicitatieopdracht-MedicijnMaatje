
# MedicijnMaatje - Technical Design Document

## Purpose

MedicijnMaatje is a backend application for managing a single user's medication list. It provides a REST API for creating, retrieving, updating and deleting medication records.

The application is built with Java 25 and Spring Boot. It runs locally and uses an embedded, file-based H2 database, eliminating the need to install or configure a separate database server.

## Architecture

The application follows a layered MVC-style architecture. Each layer has a specific responsibility to keep the application maintainable and separate concerns.

| Layer | Responsibility |
| - | - |
| Controller | Handles HTTP requests, validates incoming requests and returns HTTP responses. |
| Service | Contains business logic, enforces business rules and coordinates operations. |
| Repository | Handles database operations through Spring Data JPA. |
| Model / Entity | Represents the data stored in the database. |
| DTO | Defines the data accepted and returned by the API. |
| Exception handling | Converts application errors into appropriate HTTP responses. |

### Request Flow

1. A client sends an HTTP request to a controller.
2. The controller validates the request and calls the appropriate service method.
3. The service applies business rules, such as duplicate prevention.
4. The repository performs the required database operation.
5. The controller returns the result with an appropriate HTTP status code.

Controllers should not contain business logic or access repositories directly. DTOs should be used instead of exposing database entities directly through the API.

## Database Design

The initial version uses a single database table: `medications`.

| Column | Type | Constraints | Description |
| - | - | - | - |
| id | `BIGINT` | Primary key, generated | Unique identifier generated by the database. |
| name | `VARCHAR` | Not null, unique ignoring case | Medication name, stored in lowercase. |
| dosage | `VARCHAR` | Not null | Dosage, e.g. `500 mg` or `100 ml`. |
| usage | `VARCHAR` | Not null | Intake frequency, e.g. `2 per day` or `5 per week`. |

### Naming and Uniqueness

Medication names are trimmed and converted to lowercase before being stored.

The service layer checks whether a medication with the same name already exists. The database also enforces case-insensitive uniqueness to prevent duplicate records, including when simultaneous requests occur.

### Dosage and Usage

Dosage and usage are initially represented as strings to keep the implementation simple.

Examples:

- Dosage: `500 mg`, `100 ml`
- Usage: `2 per day`, `5 per week`

The service layer validates these values before they are stored. Only supported units and periods are accepted, and values must be positive.

This is a deliberate first-version design choice. A more structured representation would be preferable for calculations and scheduling.

## Database Configuration

H2 runs embedded inside the Spring Boot application.

The database uses file-based storage instead of in-memory storage, ensuring that medication records persist after restarting the application.

Flyway manages database schema changes through versioned SQL migration files located in:

```text
src/main/resources/db/migration/
```

Example:

```text
create_medications.sql
```

Hibernate is configured with `ddl-auto: validate`. It validates the existing schema instead of creating or modifying tables itself.

The local database files are application data and should not be committed to Git.

## REST API

The API uses `/root/medications` as its base endpoint.

| Method | Endpoint | Purpose | Expected response |
| - | - | - | - |
| GET | `/root/medications` | Retrieve all medications. | 200 OK |
| GET | `/root/medications/{id}` | Retrieve a medication by ID. | 200 OK / 404 Not Found |
| POST | `/root/medications` | Create a medication. | 201 Created / 400 Bad Request / 409 Conflict |
| PUT | `/root/medications/{id}` | Update a medication. | 200 OK / 400 Bad Request / 404 Not Found / 409 Conflict |
| DELETE | `/root/medications/{id}` | Delete a medication. | 204 No Content / 404 Not Found |

## Validation and Error Handling

Validation is performed at multiple levels:

- Request validation checks required fields and basic constraints.
- Service validation checks business rules, including dosage formats, usage formats and duplicate medication names.
- Database constraints provide a final safeguard for required fields and uniqueness.

A centralized exception handler translates errors into appropriate HTTP responses.

| Situation | HTTP status |
| - | - |
| Invalid or missing request data | 400 Bad Request |
| Medication not found | 404 Not Found |
| Medication name already exists | 409 Conflict |
| Successful creation | 201 Created |
| Successful retrieval or update | 200 OK |
| Successful deletion | 204 No Content |

Error messages should clearly explain what went wrong without exposing internal exception details.

## Testing Approach

Tests focus on the application's observable behaviour and important business rules.

| Test area | Examples |
| - | - |
| Service tests | Create medication, prevent duplicates, update medication, reject invalid dosage or usage, handle missing records. |
| Repository tests | Save and retrieve records, verify uniqueness constraints. |
| Controller tests | Verify endpoints, request validation, response bodies and HTTP status codes. |
| Integration tests | Verify the interaction between controllers, services, repositories and the database. |
| Persistence tests | Verify that records remain available after restarting the application. |

Tests should use an isolated test database or test configuration to avoid modifying the developer's normal local data.

## Future Improvements

The current implementation deliberately uses a single medication table and does not support multiple users.

Possible future improvements include:

- Separating medication information from individual medication regimens to prevent duplicate medication definitions.
- Supporting multiple users through user accounts and user-specific medication records.
- Adding authentication and authorization to protect individual medication records.
- Replacing free-form dosage and usage strings with structured values, making validation and calculations more reliable.
- Supporting more complex medication schedules and calculating upcoming intake times.

### Structured Medication Data

A future version could separate medication information from individual medication regimens.

| Table | Example columns | Purpose |
| - | - | - |
| medication_catalog | id, name | Stores each medication once. |
| user_medications | id, user_id, medication_id, dose_amount, dose_unit, frequency_count, frequency_period | Stores a user's dosage and intake instructions for a medication. |

A decimal type is preferable to an integer for dosage amounts, since some quantities may be fractional.

Units and frequency periods should use controlled values rather than arbitrary strings.

For example:

- `dose_amount = 500`
- `dose_unit = MG`
- `frequency_count = 2`
- `frequency_period = DAY`

This represents taking 500 mg twice per day.

More complex schedules, such as taking medication every eight hours or at specific times, may require a more advanced scheduling model.

### Multi-User Support

If the application is extended to support multiple users, the database could be expanded with the following tables:

| Table | Example columns | Purpose |
| - | - | - |
| users | id, name, email, password_hash | Stores user accounts. |
| medication_catalog | id, name | Stores shared medication information. |
| user_medications | id, user_id, medication_id, dose_amount, dose_unit, frequency_count, frequency_period | Links users to their medication records and instructions. |

The `user_id` and `medication_id` columns would be foreign keys.

Email addresses would be unique. Passwords must be stored using a suitable password-hashing algorithm, never as plaintext.

Authentication and authorization would also be required to ensure that users can only access their own medication records. Adding a users table alone would not provide this protection.
